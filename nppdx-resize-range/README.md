# Resize ratios: NPPDx v0.1.2 inside a fused kernel, and FKL's resize

Capability data for the paper, not timing: which zoom levels NPPDx's `Resize<J, K, Method>` accepts after a staged
operation in one kernel, and the same facts for FKL's `Resize`.

- **NPPDx:** v0.1.2 (the `nppdx` submodule, e7efdc1), operations for SM 890 (the RTX 4090) and SM 900.
- **FKL:** 3e900e6 (the `fkl` submodule of the exp3-neighborhood branch). File:line references are to that commit.
- **Measured on:** RTX 4090, CUDA 13.3, driver 610.43.02, default clocks, one launch per point.
- **Data:** `results/RTX4090/` (from `~/bvf-bench/results-nppdx-resize-range`, run at c88ebf7). Every table is in
  `results/RTX4090/tables.md`, generated by `report.py`.
  - The zoom ratios that run correctly, per method and checked by launch, are in `results/RTX4090/correct_ratios.csv`.
- **Validation of a launch:** the probe compares the output with an exact reference: NPPDx's example CPU reference
  (`example/nppdx/common/cpu_resize_reference.hpp`) with its phase computed exactly.
  - The example reference computes the phase of an output pixel in float: theta = frac((o + 0.5f) * (J / K) - 0.5f).
    At an exact center phase (theta = 0, only when J and K are both odd) this can come out just under 1, which moves
    all its taps by one pixel.
  - Seen at 7:3, 13:11 and 3:19 for every method: there the GPU's output differs from the example reference by 21 to 35
    levels (`correct_ratios.py`'s launches).
    - For bilinear, bicubic and lanczos3 at all three, and for nearest at 7:3, the GPU equals the exact reference
      (within 1 level), so the error is the example reference's.
    - Nearest at 13:11 and 3:19 is also off against the exact reference, by 29 and 35 levels. That is NPPDx's own
      nearest defect at the center phase (see "Nearest picks the next source pixel" below), not the reference's.
  - The probe takes the phase and the center index from integers, as NPPDx's kernel does, and computes the weights in
    double. At a nearest tie (theta = 1/2) both source pixels are accepted.
  - The error against the example reference is also recorded (`launch_example_max_diff...`).
  - The first run of the sweep (a4886a4) used the example reference. Its results are the same for every point of the
    sweep: no ratio of the sweep has the problem.

## Results

**Points of the sweep:** 14755 (sweep.py, `results/RTX4090/`). Every one was compiled with nvcc; every SM 890 point
that compiled was launched on the RTX 4090.
- **Ratios:** 68 named ratios from 1:49 to 41:1, plus the maxima found by NPPDx's rules over every coprime J:K up to 512.
- **Tiles:** 24 to 29 tiles from 4x2 to the largest NPPDx accepts, plus the best tiles of every ratio.
- **Compiler against the rules:** NPPDx's rules (its own constexpr functions, `probe/resize_rules.cu`) agree with the
  compiler on every point, accepted or rejected: 3451 compile and 11304 do not.
- **Probe against the rules:** for the 3451 points that compile, the probe's tiles, shared memory and block match the
  rules exactly.

### Largest factor per method, NPPDx on the RTX 4090 (SM 890)

**The pipeline:** ingest -> BoxBlur<5, 5> -> Resize<J, K, Method> -> exgest, one kernel. The factor is K/J for an upscale
and J/K for a downscale.

**The two levels in the table:**
- **"Compiles":** NPPDx's static_asserts pass.
- **"Runs, correct":** it also fits the RTX 4090's 101376 bytes of shared memory with the example's block, J divides
  the tile, and the output matches the exact reference within 1 level in the interior.

Each maximum is at the tile with the least shared memory. The shared memory shown is that of the "runs, correct" point.

| method | upscale, compiles | upscale, runs, correct | downscale, compiles | downscale, runs, correct |
|---|---|---|---|---|
| nearest | 32x (1:32, tile 4x2) | 30x (1:30, 4x2, 94080 B); 31x runs but is wrong (see nearest below) | 32x with J dividing the tile (32:1, 128x64) | 15x (15:1, 60x30, 98304 B) |
| bilinear | 32x | 31x (1:31, 4x2, 100128 B) | 32x | 12x (12:1, 48x24, 97248 B) |
| bicubic | 32x | 30x (1:30, 4x2, 97920 B) | 32x | 8x (8:1, 32x16, 87264 B) |
| lanczos3 | 32x | 29x (1:29, 4x2, 95904 B) | 32x | 6x (6:1, 24x12, 82272 B) |

**Each maximum is tight at the same tile:**
- 1:33 at 4x2 does not compile.
- 1:32 at 4x2 compiles but needs 106368 to 114624 bytes: `cudaFuncSetAttribute` fails with `cudaErrorInvalidValue`.
- The next downscale fails too: bilinear 13:1 needs 103584 bytes; bicubic 9:1 at 32x16 runs but J does not divide the
  tile (interior error 45); lanczos3 7:1 at 24x12 does not compile.

**What compiles but cannot run on the RTX 4090:**
- **Downscales from 16x (nearest), 13x (bilinear), 9x (bicubic) and 7x (lanczos3) up to 32x** compile with J dividing
  the tile. They do not fit: at 32:1, the smallest tile (128x64) needs 0.40 MB (nearest) to 2.03 MB (lanczos3). The
  downscale halo is about mu * J/K per side.
- **Ratios where J does not divide the tile** compile up to 32.125x upscale (8:257) and 39.9x downscale (479:12,
  searching J, K <= 512). They cannot be correct, as below.

**Ratios that have a correct configuration on the RTX 4090.** By NPPDx's rules, only 248 (nearest), 240 (bilinear), 213
(bicubic) and 192 (lanczos3) of all coprime J:K up to 512 have a tile that compiles, fits with the example's block and
that J divides (`results/RTX4090/feasible_ratios.csv`).
- J <= 18, 17, 15 and 14; K <= 31, 31, 30 and 29.
- The ratios closest to 1 (upscale and downscale) are 14:15 and 15:14 for nearest and bilinear, 14:15 and 14:13 for
  bicubic, and 13:14 and 14:13 for lanczos3 (`results/RTX4090/tables.md`).
- **Launched once each at its best tile** (`correct_ratios.py`, `results/RTX4090/correct_ratios.csv`):

  | method | rules | correct | factors (K/J) of the correct ones | not correct |
  |---|---|---|---|---|
  | nearest | 248 | 238 | 0.0667 (15:1) to 30 (1:30) | 13:5, 13:11, 7:23, 5:23, 5:27, 3:19, 3:25, 1:25, 1:29, 1:31 (22 to 35 levels) |
  | bilinear | 240 | 240 | 0.0833 (12:1) to 31 (1:31) | none |
  | bicubic | 213 | 213 | 0.125 (8:1) to 30 (1:30) | none |
  | lanczos3 | 192 | 192 | 0.167 (6:1) to 29 (1:29) | none |
- **16:15 and 15:16** (e.g. 1920 -> 1800) have no correct tile on the RTX 4090. The smallest tiles that J divides need
  106176 to 123552 bytes.
- **135:28 (1080 -> 224)** has no correct tile on either SM. A tile that 135 divides is at least 540 x 270, so the
  tiles that compile all give wrong output: interior errors of 26 to 66 levels.
- **The ratios of the paper's workload run correctly:**
  - 5:16 (20x10 tile -> 64x32, 43776 B);
  - 1:2 (every tile of the grid up to 40x20; 32x32 and larger exceed the shared memory);
  - 3:4 (12x6 to 48x24).

**When J does not divide the tile, the output is wrong.**
- Of the 173 launched points where J does not divide the tile, 172 are off by 2 to 88 levels in the interior.
- The exception, bilinear 8:249 at 4x2 (31.1x), stays within 1 level in the interior but is off by 20 at the edges.
- Of the 790 launched points where J divides the tile, 788 are within 1 level. The other 2 are the nearest points
  below.
- Every launched point gives the same output with 32 threads per block as with the example's one thread per cell.

**Nearest picks the next source pixel at the center phase** (where a source pixel's center falls exactly on an output
pixel's sampling position) at 10 of its 248 ratios: 13:5, 13:11, 7:23, 5:23, 5:27, 3:19, 3:25, 1:25, 1:29 and 1:31.
Interior errors are 22 to 35 levels.
- NPPDx takes the center index from integers (`detail/backend/resize_operations.hpp:155-163`) but the phase theta in
  float (`:146-153`). With one tap (nearest), theta chooses the start index (`:171-189`).
- nvcc contracts `(n + 0.5f) * (J / K) - 0.5f` into a fused multiply-add. Where float(J/K) is below J/K, theta can come
  out just under 1 instead of 0.
- All 10 are odd:odd ratios (the only ones with exact center phases) whose float(J/K) is below J/K. For 1:K that is
  K = 25, 29 and 31 among the odd K <= 31.
  - The condition is necessary but not sufficient: 19 other odd:odd ratios with float(J/K) below J/K come out correct.
- With `-fmad=false`, 1:25 and 1:31 are exact (interior and edge error 0).
- The other methods have an even number of taps, for which theta does not choose the start index; none of their
  launches has this error.
- In the sweep: 1:29 and 1:31. The other 8 are in `correct_ratios.csv`.

**The block:**
- **On SM 890** the example's block (one thread per 4x2 cell of the output tile, or of the input tile for a downscale)
  never exceeds 1024 threads at a point that fits the shared memory: for every ratio up to 512 and every tile, the same
  tiles fit with and without the block's limit.
- **On SM 900** it does: one thread per cell limits the upscale to 32x (1:32 at 4x2, 1024 threads, 106368 B).
  - The 227 KB of shared memory allow 48x (nearest, bilinear), 47x (bicubic) and 46x (lanczos3) with a block of at most
    1024 threads. This pipeline's steps are strided, as the 32-thread launches above show.

**SM 900** (compiled, not launched, as there is no SM 90 GPU here; limit 227 KB, NPPDx's table):

| method | upscale, compiles | upscale, fits 227 KB, J divides, any block <= 1024 | same with the example's block | downscale, fits 227 KB, J divides |
|---|---|---|---|---|
| nearest | 49x (1:49, 4x2) | 48x (1:48, 232320 B) | 32x | 24x (24:1, 96x48, 229728 B) |
| bilinear | 49x | 48x (232320 B) | 32x | 19x (19:1, 76x38, 230304 B) |
| bicubic | 49x | 47x (228480 B) | 32x | 13x (13:1, 52x26, 216384 B) |
| lanczos3 | 49x | 46x (224832 B) | 32x | 10x (10:1, 40x20, 213600 B) |

**What the compiler says.** Over 11304 rejected points (`results/RTX4090/tables.md`):
- **"This operation configuration is not supported"** (10328 points): the exgest's `is_supported_v` on the output tile.
  - It comes before the resize's own "derived output tile is not supported" text, which never appears.
- **"tuple index must be in range"** (940 points): the output tile has a zero dimension (2 N K <= J). Its storage type is
  an empty tuple.
  - NPPDx's "tile is too small for the given downscale ratio" never appears.
- **"Resize configuration is invalid: the derived intermediate tile is not supported for this SM/cell layout. Reduce
  TileSize or resize ratio (K/J), or use a staged resize."** (36 points).

## NPPDx: what bounds the ratio

The pipeline is NPPDx's example `04_resize/fused_resize.cu` without its color conversion: ingest (RGB24) -> BoxBlur<5, 5>
-> Resize<J, K, Method> -> exgest (RGB24), one kernel. Every tile is in shared memory as 3 float channels.

**Paths below:** `include/nppdx/` of v0.1.2. `fn` = `detail/database/function/function_operation_implementation.hpp`.

**The ratio is a compile-time type.**
- `Resize<J, K, Method>`: J input samples to K output samples, the same J:K on both axes (`operators/function.hpp:531-543`).
  J and K must be coprime (`function.hpp:537`).
- A kernel handles one ratio. A different zoom level is a different kernel instantiation.
- No register path: "Register-based execute not supported for resize operations." (`fn:545-550`).

**The halo of the resize** is h = floor(mu * max(1, J/K) + 1/2) input pixels per side (`radius_ceil`,
`function.hpp:547-556`). mu is 1/2 (nearest), 1 (bilinear), 2 (bicubic) or 3 (lanczos3) (`function.hpp:568-576`).
- Upscale: h = 1, 1, 2, 3 for the four methods.
- Downscale: h grows with J/K, e.g. 12 (bilinear) and 36 (lanczos3) at 12:1.
- NPPDx's documentation says of nearest "No halo required", but the code gives it a halo of 1 when upscaling.

**The tiles of the resize**, for an input tile N (per axis):
- **Output tile:** O = ceil((2 N K - J) / (2 J)) (`detail/backend/resize_geometry.hpp:27-36`, `fn:516-522`).
  - If J divides N, O = N K / J.
- **Intermediate tile (the separable pass):** O_x x (N_y + 2h) (`function.hpp:587-597`, `fn:524`).
- **Ingest tile and blurred tile:** N + 2(2 + h) per axis (the box's halo of 2 plus h).

**Shared memory of the pipeline** (four tiles of 12-byte pixels, `compute_total_tile_storage`):

    smem = 12 B x [ 2 (N_x + 4 + 2h)(N_y + 4 + 2h) + O_x (N_y + 2h) + O_x O_y ]

**What NPPDx checks at compile time.** A point that fails any of these does not compile.
- **The input tile,** `is_supported_v` of every description (`detail/nppdx_execution.hpp:54-55`), which is
  `is_valid_tile_v` (`detail/database/cell_config.hpp:66-81`):
  - x a multiple of 4 and y a multiple of 2 (the 4x2 cell, `cell_config.hpp:63`);
  - 12 x y bytes within the SM's shared memory in commondx's table: 99 KB for SM 890, 227 KB for SM 900
    (`commondx/device_info_shared_memory.hpp:31-50`).
- **2 N K >= J on both axes** (`fn:518-521`): "tile is too small for the given downscale ratio".
- **`is_valid_tile_v` of the output tile O** (`fn:530`, `fn:534-537`). The exgest's TileSize is O, so its own
  `is_supported_v` fails with it.
  - In the sweep this fails first as "This operation configuration is not supported".
- **`is_valid_tile_v` of the intermediate tile** (`fn:531-532`, `fn:538-540`).
- The comment at `fn:527-528`: "Large upscale factors can produce output/intermediate tiles that cannot be represented
  by this shared-memory execution model."

**What NPPDx does not check:**
- **The sum of the four tiles.** `is_valid_tile_v` checks each tile alone against the SM's table. A point can compile and
  still need more shared memory than the device has. Then `cudaFuncSetAttribute(..., MaxDynamicSharedMemorySize)` fails
  with `cudaErrorInvalidValue` and the kernel cannot launch.
  - The RTX 4090's `cudaDevAttrMaxSharedMemoryPerBlockOptin` is 101376 bytes, measured.
- **The block.** The example launches one thread per 4x2 cell: of the ingest's tile for a downscale, of the exgest's
  (output) tile otherwise (`fused_resize.cu:305-307`, `detail/database/operation_database.hpp:37-39`). A block has at
  most 1024 threads.
  - Every step of this pipeline loops over its cells with a stride (`Strided=true`), so a smaller block also works.
    Measured: every point gives the same output with 32 threads per block.
- **That J divides the tile.** `fn:517`: "Assumes Layout::base_x and Layout::base_y are divisible by J". Nothing checks
  it.
  - Points where J does not divide the tile compile and run but give wrong output (measured, below).
  - With the 4x2 cell, many such points fail anyway, because O is then not a multiple of the cell. For example, 3:2
    compiles only with tiles that 3 divides.

**The largest upscale** is at the smallest tile, 4x2. With J = 1, O = 4K x 2K:
- **Compiles:** 12 x 4K x 2K <= 99 KB, so K <= 32 on SM 890 (and K <= 49 on SM 900, 227 KB).
- **Fits the RTX 4090:** the sum of the four tiles must also fit 101376 bytes, so K <= 31 (nearest, bilinear), 30
  (bicubic) and 29 (lanczos3). The larger halos of bicubic and lanczos3 take the difference.
- **Ratios with J > 1:** they need tiles that are multiples of J and outputs that are multiples of the cell, so they
  reach less, except where J does not divide the tile, which gives wrong output.

**NPPDx's documentation** (README, https://nvidia.github.io/NPPDx/: requirements, area steps, performance, release
notes) gives no limit on the ratio, the tile or the shared memory.
- The only constraint on the resize it states is "coprime J and K".
- None of the words "modest", "moderate", "upscale", "downscale" or "staged" appear there.
- The limit is stated only in code comments:
  - `fused_resize.cu:22-25`: "this kernel keeps a full resized RGB tile in shared memory before color convert and
    exgest. That only works for modest tiles; in practice there is often not enough SMEM to stage the entire resized
    image, so a dedicated path (e.g. exgestResize ...) will replace this pattern".
  - `fn:527-528` (above). The static_assert texts suggest "use a staged resize".

## FKL's resize (3e900e6)

Paths: `include/fused_kernel/`. `resize.h` and `interpolation.h` are in `algorithms/image_processing/`.

**The factor is a run-time value per plane.**
- `ResizeParams` holds `Size dstSize` and `float2 src_conv_factors` (`resize.h:44-58`).
- `build()` computes them on the host from the source size of the operation it reads from and the destination size:
  `cf = dst / src` in double, stored as the float 1/cf (`resize.h:266-278`, `resize.h:164-205` for the aspect-ratio
  variants).
- A different zoom level is a different parameter, not a different kernel.

**The sampling:** `src = thread * factor` (`resize.h:117-123`), then bilinear interpolation:
- floor and floor + 1, the right and bottom neighbours clamped to the last column and row (`interpolation.h:70-103`);
- 4 evaluations of the producer per output value (`interpolation.h:94-97`). Each one runs the whole chain before the
  resize (for example ReadNV12 -> YUVToRGB -> Crop).

**The interpolation modes:** `InterpolationType { INTER_LINEAR = 1, NONE = 17 }` (`interpolation.h:31-34`). Only
INTER_LINEAR has an implementation (`interpolation.h:45-105`), so the resize is bilinear only. The mode is a template
parameter (`resize.h:126`).

**Bounds on the factor:** none.
- The static_asserts of `resize.h` (lines 46, 73, 118, 153, 155, 167, 268, 282) are about operation types. None is
  about sizes or the factor.
- Any up or down factor builds and runs. A downscale has no prefilter: it is always 4 taps.

**Shared memory:** none.
- `TransformDPP` launches with 0 bytes of dynamic shared memory (`core/execution_model/executors.h:496`, `:498`,
  `:520`).
- There is no `__shared__` in `data_parallel_patterns.h`, `executors.h`, `resize.h`, `interpolation.h` or `crop.h`.
- Each thread computes its output values from the producer chain in registers.

**Different ratios in one launch:** yes. `Crop<>::build(std::array<Rect, N>)` followed by `Resize::build(Size)` gives
every plane its own resize, with its own source size and factors:
- `BackFuser` hands every plane's crop to Resize's batch builder (`core/execution_model/operation_model/iop_fuser.h:72-89`).
- The builder builds one Resize per plane (`batch_operations.h:129-149`, `resize.h:280-284`, `resize.h:266-277`).
- Every plane's parameters are stored in `BatchReadParams::opData` (`batch_operations.h:101-105`). The kernel picks
  them with `thread.z` (`batch_operations.h:207-212`).
- **The paper's workload already does this:** `BENCH_REGIONS=mixed` (`common/bench_geometry.cmake:3`, "the paper's
  workload") resizes 20x10, 32x16 and 48x24 crops to 64x32 in one launch.
  - That is 5:16, 1:2 and 3:4 in the same kernel: results-v3's fkl-vs-npp, fkl-vs-opencv-cuda and fkl-ablation.
  - NPPDx's programs are built for one region size because a kernel has one J:K (`fkl-vs-nppdx/CMakeLists.txt`,
    `fkl-vs-nppdx/benchmarks/nppdx_common.h:53-54`).

**Limits on region and output sizes:** nothing in FKL bounds them, but CUDA's grid limits apply.
- Sizes are run-time ints.
- The grid is ceil(max width / block.x) x ceil(max height / block.y) x planes (`executors.h:459-463`). The width and
  height are the maxima over the planes (`batch_operations.h:367-376`).
- The number of planes is a template parameter (`BATCH`).
- The bounds check is against those maxima (`core/execution_model/data_parallel_patterns.h:234-237`). In the paper's
  pipeline every plane has the same output size (64x32).

## Reproduce

    cd bvf-paper-bench
    nppdx-resize-range/sweep.py <output directory> --max-jk 512    # about 40 minutes on 30 threads, needs the GPU
    nppdx-resize-range/report.py <output directory> <tables.md>
    nppdx-resize-range/correct_ratios.py <work directory> <correct_ratios.csv>  # about 8 minutes

- `probe/resize_probe.cu`: one point, compiled with `-DPROBE_J/K/METHOD/TX/TY/SM`. It prints its tiles, shared memory and
  block.
  - `--launch [threads]` runs it once against the exact reference and NPPDx's example CPU reference, both after a 5x5
    box (Validation, above).
  - The references replicate the blurred image's edge, while the kernel blurs the replicated input, so the comparison
    is also given for the interior: output pixels whose window is inside the image.
- `probe/resize_rules.cu`: NPPDx's constexpr functions (the halo, `compute_storage_config`, `is_valid_tile_v`,
  `compute_channels_storage`, the cell count), evaluated at run time over every coprime J:K and every tile NPPDx accepts.
- `sweep.py`: the rules, the points, the compilation (nvcc 13.3, `-arch=sm_89` / `sm_90`, `--expt-relaxed-constexpr` as
  NPPDx's CMake package) and the launches.
- The nearest check (1:25; add `-fmad=false` for the exact result):

      nvcc -std=c++20 -O3 -arch=sm_89 --expt-relaxed-constexpr -Inppdx/include -Inppdx/example/nppdx/common \
           -DPROBE_J=1 -DPROBE_K=25 -DPROBE_METHOD=nearest -DPROBE_TX=4 -DPROBE_TY=2 -DPROBE_SM=890 \
           nppdx-resize-range/probe/resize_probe.cu -o probe && ./probe --launch
